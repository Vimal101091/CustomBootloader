Platform-Agnostic Bootloader

One C11 boot policy, one platform interface, and a native port for each target. The first release authenticates and boots a single application image. UART recovery and A/B OTA build on that flow.

Boot flow and platform boundary

OperationPort contract
find_image()Return an opaque handle to the candidate. The port owns flash addresses and partition details.
verify_image()Authenticate the candidate and check target compatibility using the configured trust root and image format.
start_image()Validate the native entry state and transfer control to the same bytes that were authenticated.
recover()Report the failure and enter recovery or stop safely. A replacement image goes through normal verification before launch.

Authenticate or protect the loader and its trust configuration at an earlier stage. Build each target from the same core plus its native port. A distribution bundle can carry multiple target builds.

Platform ports

STM32 NUCLEO-F446RE

Read a signed manifest and firmware payload from internal flash. Validate the application vector table, initial stack pointer, and reset handler. Prepare the Cortex-M state and branch to the application.

Proposed lab layout: loader 0x08000000, manifest 0x08010000, app vector table 0x08010200. Link Blinky at the app address and check that the loader fits in 64 KiB.

STM32F446 flash reference

ESP-IDF

Integrate with the second-stage bootloader for the chosen chip and SDK version. Resolve the candidate from the partition table and use native image authentication with Secure Boot configured. Keep native loading and handoff.

If the native API combines verification and loading, preserve the rule that control can transfer only after the chosen image is authenticated.

ESP-IDF bootloader guide

Hosted simulator

Use files or fixtures for image storage, inject errors, and record the requested handoff. Run the same policy tests before testing real hardware.

x86-64 UEFI

Read the package through firmware storage services. Authenticate it and launch the verified EFI executable through firmware image services.

CRC, UART, and OTA

PathShared rulePlatform responsibility
CRCFor a shared UART protocol, specify the CRC variant and covered bytes. Reject or retry damaged frames. Authenticate the complete image separately.Use software or hardware CRC with the same parameters. Native transfer protocols can use their own integrity checks.
UART recoveryEnter recovery on a boot failure or a supported recovery trigger. For a common protocol, share framing, sequence checks, and bounded retries.Set up UART and write only the permitted flash region. When using ROM recovery, the vendor ROM handles transfer. The loader authenticates the application at the next boot.
OTA with A/B slotsPublish a pending candidate only after the full image is durable and verified. Boot it on a limited trial and fall back if it fails to confirm.The running app downloads into the inactive slot. The port provides durable boot state or uses native state, such as ESP-IDF OTA metadata. The app confirms after its health checks.

A/B update lifecycle

Write inactive slot → verify → mark pending → trial boot → confirm

An interrupted write leaves the confirmed slot selected. A failed or exhausted trial returns to the confirmed slot. Commit boot-state changes durably before the next transition. A single-slot UART update can require reflashing after a power cut.

Bring-up and acceptance

  1. Simulator. Confirm that valid images reach handoff and missing, corrupted, or wrong-target images reach recovery. Inject a read failure and a rejected handoff.
  2. F446RE. Flash the loader and signed Blinky through ST-LINK. Check that LD2 blinks with the valid image. Corrupt the payload without re-signing and check that recovery runs.
  3. ESP-IDF. Confirm that native verification gates launch. When adding OTA, test confirmation, failed trials, and power loss during update and boot-state writes.
